# Security Lab - Nmap Network Reconnaissance

## Objective

Use Nmap from Kali Linux to perform network reconnaissance against the Ubuntu Server and Ubuntu Desktop VMs.

The goals of this lab were to:

* Discover active hosts on the homelab network
* Identify open and closed TCP ports
* Identify services running on exposed ports
* Determine service versions
* Gather basic operating system information
* Compare externally visible services with services actually listening on the Ubuntu Server
* Analyze the security implications of exposed network services

---

| VM             | IP Address  | Role                            |
| -------------- | ----------- | ------------------------------- |
| Kali Linux     | `10.0.0.30` | Security/reconnaissance machine |
| Ubuntu Desktop | `10.0.0.20` | Secondary target                |
| Ubuntu Server  | `10.0.0.10` | Target server                   |

Network:

10.0.0.0/24

# 3. Basic Port Scan - Ubuntu Server

The Ubuntu Server was scanned using Nmap's default TCP scan:

```bash
nmap 10.0.0.10
```

Results:

```text
Not shown: 998 filtered tcp ports (no-response)

PORT   STATE SERVICE
22/tcp open  ssh
80/tcp open  http

MAC Address: 08:00:27:8E:2E:20
```

### Findings

Two TCP ports were identified as open:

| Port   | State | Service |
| ------ | ----- | ------- |
| 22/tcp | Open  | SSH     |
| 80/tcp | Open  | HTTP    |

The remaining 998 scanned TCP ports were reported as filtered because Nmap received no response.

This established that the Ubuntu Server was exposing two network services:

* SSH for remote administration
* HTTP for the Apache web server

---

# 4. Service and Version Detection

Nmap was then used to identify the software and versions running on the open ports:

```bash
nmap -sV 10.0.0.10
```

Results:

```text
Not shown: 998 filtered tcp ports (no-response)

PORT   STATE SERVICE VERSION
22/tcp open  ssh     OpenSSH 10.2p1 Ubuntu 2ubuntu3.5 (Ubuntu Linux; protocol 2.0)
80/tcp open  http    Apache httpd 2.4.66 ((Ubuntu))

MAC Address: 08:00:27:8E:2E:20 (Oracle VirtualBox virtual NIC)

Service Info: OS: Linux; CPE: cpe:/o:linux:linux_kernel
```

### Findings

Nmap identified:

**SSH**

```text
OpenSSH 10.2p1 Ubuntu 2ubuntu3.5
```

**HTTP**

```text
Apache httpd 2.4.66
```

Nmap also identified the operating system family as Linux.

This demonstrates the additional information an attacker can obtain beyond simply discovering that a port is open.

Instead of seeing:

```text
22/tcp open ssh
```

an attacker can potentially determine the specific SSH implementation and version. Noted.

---

# 5. Full TCP Port Scan

A full TCP port scan was performed to check all 65,535 TCP ports:

```bash
nmap -p- 10.0.0.10
```

Results:

```text
Not shown: 65533 filtered tcp ports (no-response)

PORT   STATE SERVICE
22/tcp open  ssh
80/tcp open  http

MAC Address: 08:00:27:8E:2E:20
```

### Findings

Only two open TCP ports were identified across the full TCP port range:

```text
22/tcp
80/tcp
```

The remaining 65,533 ports were filtered.

This confirmed that the initial Nmap scan had not missed additional open TCP services outside its default scan range.

---

# 6. Aggressive Nmap Scan

An aggressive scan was performed to gather additional information:

```bash
nmap -A 10.0.0.10
```

Results again identified:

```text
22/tcp open  ssh
80/tcp open  http
```

Nmap identified:

```text
OpenSSH 10.2p1 Ubuntu 2ubuntu3.5
Apache httpd 2.4.66
```

Additional HTTP information was discovered:

```text
http-title: Site doesn't have a title (text/html).
http-server-header: Apache/2.4.66 (Ubuntu)
```

### OS Detection

Nmap attempted to determine the operating system but reported that the results may be unreliable:

```text
Warning: OSScan results may be unreliable because we could not find at least 1 open and 1 closed port
```

Nmap produced several possible Linux/Android-related guesses but did not find an exact OS match.

Therefore, the OS scan was treated as **inconclusive** rather than as definitive identification.

### Network Distance

Nmap reported:

```text
Network Distance: 1 hop
```

This was consistent with the Ubuntu Server being directly reachable from the Kali VM within the homelab network.

# 8. Test the Apache Web Server

The HTTP service discovered on Ubuntu Server was tested directly from Kali:

```bash
curl http://10.0.0.10
```

The Apache web server responded successfully.

This confirmed that the service discovered by Nmap was not only listening on TCP port 80 but was also accepting HTTP requests.

---

# 9. Compare Nmap Results With the Server

After scanning the server externally, the Ubuntu Server's listening sockets were checked locally:

```bash
sudo ss -tulpn
```

The server showed listening services associated with:

```text
22/tcp
80/tcp
```

These results matched the open ports discovered by Nmap.

This provided an important comparison:

```text
External View                    Internal View

Kali                            Ubuntu Server
 |                                   |
 |--- Nmap ---> 22/tcp open          |
 |--- Nmap ---> 80/tcp open          |
 |                                   |
 |                              ss -tulpn
 |                                   |
 |                         22/tcp listening
 |                         80/tcp listening
```

The Nmap results therefore accurately reflected the services exposed by the Ubuntu Server.

# Security Analysis

The most important finding from this lab was the difference in network exposure between Ubuntu Server and Ubuntu Desktop.

Ubuntu Server exposed two services:

```text
SSH
HTTP
```

Each exposed service represents a potential attack surface.

For example:

* SSH provides remote administrative access and therefore requires strong authentication and appropriate access controls.
* Apache provides a web service that can potentially be targeted through vulnerabilities or application-level attacks.

The reconnaissance process demonstrated how an attacker could gather this information without having administrative access to the target machine.

Nmap was able to determine:

* Which hosts were active
* Which ports were open
* Which services were exposed
* Which software versions were running
* Basic operating system information
* HTTP server information

This information could then be used to determine what additional attacks or vulnerabilities might be relevant.

---

# Key Takeaways

### 1. Open ports reveal attack surface

The Ubuntu Server exposed SSH and HTTP, while Ubuntu Desktop exposed no open TCP ports in the scan.

### 2. Service enumeration provides more information

Using:

```bash
nmap -sV
```

provided specific software and version information instead of simply identifying the service.

### 3. Full port scans are useful

Using:

```bash
nmap -p-
```

confirmed that no additional open TCP ports were discovered outside the default scan range.

### 4. Automated OS detection isn't always reliable

The aggressive scan produced multiple possible OS guesses and explicitly warned that the results were unreliable.

OS detection should therefore be treated as an indication rather than definitive proof.

### 5. External reconnaissance can be compared with internal configuration

Comparing:

```bash
nmap -sV 10.0.0.10
```

with:

```bash
sudo ss -tulpn
```

showed that the externally visible services matched the services listening on the server.

# Conclusion

This lab demonstrated the reconnaissance phase of a basic security assessment.

Using Kali Linux and Nmap, the homelab network was mapped and the exposed services on the Ubuntu Server were identified. The server exposed SSH and Apache HTTP services, while the Ubuntu Desktop did not expose any open TCP ports in the scanned range.

The results also demonstrated how service/version detection can provide an attacker with information about the software running on a target. Comparing Nmap's external view with `ss -tulpn` on the server confirmed that the discovered services corresponded to actual listening services.

This lab provides me a foundation for future security exercises involving **service enumeration, SSH security, web-server security, port-scan detection, and intrusion detection**.
