# Security Lab - Apache Enumeration & Hardening

## Overview

This lab focused on using Kali Linux to perform reconnaissance and enumeration against an Apache web server running on an Ubuntu Server VM.

The goal was to identify what information an attacker could discover remotely, investigate exposed web resources, examine Apache's configuration, and then reduce unnecessary information disclosure through Apache hardening.

## Lab Environment

| VM             | IP Address  | Role                   |
| -------------- | ----------- | ---------------------- |
| Kali Linux     | `10.0.0.30` | Security / Enumeration |
| Ubuntu Desktop | `10.0.0.20` | Not used in this lab   |
| Ubuntu Server  | `10.0.0.10` | Apache Web Server      |

---

## Objectives

* Identify open ports on the Ubuntu Server
* Identify the web server and version
* Examine HTTP response headers
* Enumerate accessible web resources
* Investigate `/server-status`
* Examine Apache configuration
* Identify unnecessary information disclosure
* Harden Apache to reduce version disclosure
* Verify the security improvement from Kali

---

# 1. Verify Apache

On Ubuntu Server, Apache was verified with:

```bash
sudo systemctl status apache2
```

Apache was running successfully.

The listening port was verified with:

```bash
sudo ss -tlnp | grep :80
```

Apache was listening on TCP port `80`.

---

# 2. Basic Nmap Enumeration

From Kali:

```bash
nmap 10.0.0.10
```

The scan identified:

```text
PORT   STATE SERVICE
22/tcp open  ssh
80/tcp open  http
```

### Findings

* TCP `22` was open for SSH.
* TCP `80` was open for HTTP.
* The presence of port 80 indicated that a web server was available for further enumeration.

# 5. HTTP Resource Enumeration

Apache resources were enumerated using:

```bash
nmap --script http-enum -p 80 10.0.0.10
```

Additional directory/file enumeration was performed with Gobuster:

```bash
gobuster dir -u http://10.0.0.10 -w /usr/share/wordlists/dirb/common.txt
```

The following resources were identified:

```text
.hta          403 Forbidden
.htaccess     403 Forbidden
.htpasswd     403 Forbidden
index.html    200 OK
server-status 403 Forbidden
```

### Interpretation

The resources were discoverable, but discovery did not mean they were accessible.

For example:

```text
.htpasswd → 403 Forbidden
```

This indicates that Apache prevented access to the resource.

This is an important security concept:

> Discovery of a resource does not necessarily mean that the resource is vulnerable or accessible.

# 6. Investigating /server-status

The `/server-status` endpoint was discovered during enumeration.

From Kali:

```bash
curl http://10.0.0.10/server-status
```

<img width="633" height="216" alt="image" src="https://github.com/user-attachments/assets/93929612-9cfb-4dc4-ad6e-d6e4975398e8" />


The response was:

```text
403 Forbidden
```

The Apache configuration was then investigated.

On Ubuntu Server:

```bash
sudo apache2ctl -M | grep status
```

The output showed:

```text
status_module (shared)
```

This confirmed that Apache's `mod_status` module was enabled.

The configuration was examined with:

```bash
sudo grep -R "server-status" /etc/apache2/
```

The configuration contained:

```apache
<Location /server-status>
    SetHandler server-status
</Location>
```

The `status.conf` file was then examined:

```bash
sudo cat /etc/apache2/mods-enabled/status.conf
```

The configuration included:

```apache
Require local
```

### Why Kali Received 403

The Apache server was:

```text
10.0.0.10
```

Kali was:

```text
10.0.0.30
```

Because `/server-status` required a local request, Kali was denied access.

Therefore:

```text
Kali
10.0.0.30
      |
      | GET /server-status
      v
Ubuntu Server
10.0.0.10
      |
      | Require local
      v
403 Forbidden
```

This demonstrated that the endpoint existed but was protected by Apache access controls.

# 7. Apache Security Configuration

The Apache security configuration was examined:

```bash
sudo nano /etc/apache2/conf-available/security.conf
```

The original configuration contained:

```apache
ServerTokens Full
ServerSignature Off
```

`ServerSignature` was already set to:

```apache
ServerSignature Off
```

No change was necessary for this setting.

The setting that was changed was:

```apache
ServerTokens Full
```

---

# 8. Apache Hardening

The configuration was changed from:

```apache
ServerTokens Full
```

to:

```apache
ServerTokens Prod
```

`ServerSignature Off` was left unchanged.

Apache was then restarted:

```bash
sudo systemctl restart apache2
```

The service status was verified:

```bash
sudo systemctl status apache2
```

Apache returned to an active/running state.

# Key Takeaways

### 1. Enumeration can reveal useful information without exploitation

A remote attacker was able to determine:

* The server had HTTP available
* Apache was running
* The Apache version was exposed
* Certain web resources existed
* `/server-status` was present

No authentication or exploitation was required to obtain this information.

### 2. A discovered resource is not necessarily an exposed resource

Resources such as:

```text
.htpasswd
/server-status
```

were identified but returned:

```text
403 Forbidden
```

Apache's access controls prevented unauthorized access.

### 3. Information disclosure is still a security consideration

The original response:

```text
Server: Apache/2.4.66 (Ubuntu)
```

gave a remote client more information than was necessary.

Changing:

```apache
ServerTokens Full
```

to:

```apache
ServerTokens Prod
```

reduced the amount of information Apache disclosed.

### 4. Logs provide the defensive perspective

The reconnaissance performed from Kali generated entries in Apache's access logs.

This demonstrates how security personnel can investigate web requests and potentially identify reconnaissance activity.

# Conclusion

This lab demonstrated the process of enumerating and assessing an Apache web server from a security perspective.

Kali was used to discover the exposed HTTP service, identify Apache and its version, enumerate web resources, investigate `/server-status`, and observe the HTTP information returned by the server.

The Apache configuration was then examined and hardened by changing `ServerTokens` from `Full` to `Prod`. The server was subsequently tested again from Kali to verify that less information was being disclosed.

The lab demonstrated to me basic web security
