# Scenario 02: Incorrect Default Gateway

## Objective

The purpose of this lab was to understand the role of the **default gateway** in network communication and to practice troubleshooting a common networking issue.

This scenario demonstrates that:
- Devices on the same subnet can still communicate without a correct default gateway.
- Traffic destined for external networks relies on the default gateway.
- An incorrect default gateway causes internet connectivity to fail while local communication continues to work.

---

# Initial Network Configuration

Before introducing the issue, the routing table was:

```bash

```

Example:

```text

10.0.0.0/24 dev enp0s8 proto kernel scope link src 10.0.0.20
10.0.2.0/24 dev enp0s3 proto kernel scope link src 10.0.2.15
```

The default gateway (`10.0.2.2`) was provided by the VirtualBox NAT network.

# Introducing the Problem

The goal was to intentionally configure an incorrect default gateway.

Changed the gateway from:

```text
10.0.2.2
```

to

```text
10.0.2.254
```

This IP address does not exist on the NAT network.

---

# Unexpected obstacle

Initially, I attempted to edit the Netplan configuration.

Opened:

```bash
sudo nano /etc/netplan/01-network-manager-all.yaml
```

The file only contained:

```yaml
network:
  version: 2
  renderer: NetworkManager
```

### Discovery

Ubuntu Desktop was using **NetworkManager** to manage networking instead of a manually configured Netplan YAML file.

The actual network configuration was stored inside NetworkManager connection profiles.

# Another Hiccup

The graphical Network settings repeatedly reverted to **Automatic (DHCP)** whenever Manual mode was selected.

Instead of using the GUI, I investigated the connection profile directly:



# Troubleshooting Process

## Step 1

Check routing table.

```bash
ip route
```

Observed:

```text
default via 10.0.2.254
```

Immediately indicated an incorrect default route.

---

## Step 2

Verify local connectivity.

```bash
ping -c 4 10.0.0.10
```

Succeeded.

Conclusion:

- Interface was operational.
- IP configuration was correct.
- Internal network was healthy.

---

## Step 3

Verify external connectivity.

```bash
ping -c 4 8.8.8.8
```

Failed.

Conclusion:

Only off-subnet communication was affected.

---

# Root Cause

The default gateway was incorrectly configured.

Linux attempted to forward all traffic destined outside the local networks to:

```text
10.0.2.254
```

Since that gateway did not exist, external communication failed.

---

# Resolution

Restored the correct gateway.

```bash
sudo nmcli connection modify netplan-enp0s3 ipv4.gateway 10.0.2.2
```

Restarted the connection:

```bash
sudo nmcli connection down netplan-enp0s3
sudo nmcli connection up netplan-enp0s3
```

Verified:

```bash
ip route
```

# Lessons Learned

- The default gateway is only used for destinations outside directly connected networks.
- Devices on the same subnet communicate directly without using the gateway.
- A successful local ping combined with a failed internet ping often indicates a routing or gateway issue.
- `ip route` should be one of the first commands used when diagnosing network connectivity problems.
- Ubuntu Desktop may use **NetworkManager** instead of manual Netplan YAML configuration, meaning network settings are managed through connection profiles.
- The `nmcli` utility is a reliable way to inspect and modify NetworkManager-managed connections from the command line.

---

# Key Takeaways

- Local subnet communication does **not** require the default gateway.
- Internet communication **does** require a valid default gateway.
- Routing issues can often be identified quickly by examining the routing table before investigating higher-level services.
- Understanding how NetworkManager interacts with Netplan is important when administering Ubuntu Desktop systems.
