# Firewall Blocking SSH - Network Troubleshooting Lab

## Objective

The objective of this lab was to simulate a common network troubleshooting scenario where SSH access to a server suddenly becomes unavailable due to a firewall configuration issue. The goal was to practice a structured troubleshooting methodology to identify the root cause instead of immediately assuming the problem.

---

# Lab Environment

| Machine | Role | IP Address |
|----------|------|------------|
| Ubuntu Server | SSH Server | 10.0.0.10 |
| Ubuntu Desktop | Client | 10.0.0.20 |
| Kali Linux | Troubleshooting Client | 10.0.0.30 |

---

# Prerequisites

Before beginning the lab, the following conditions were verified:

- Ubuntu Server was powered on
- SSH service was installed
- SSH service was running
- UFW firewall was enabled
- SSH connections from Kali were successful

Baseline verification:

```bash
sudo systemctl status ssh
sudo ufw status
ssh vboxuser@10.0.0.10
```

At this stage, SSH connectivity was functioning normally.

---

# Scenario

A user reports that they are no longer able to SSH into the Ubuntu Server.

No other information is provided.

Instead of assuming the cause, the objective is to investigate the problem using a logical troubleshooting process.

---

# Simulating the Problem

To intentionally create the issue, the SSH firewall rule was removed from the Ubuntu Server.

```bash
sudo ufw delete allow ssh
```

After removing the rule, the firewall configuration was verified.

```bash
sudo ufw status
```

The rule allowing TCP port 22 was no longer present.

---

# Symptoms

Attempting to SSH from Kali resulted in a failed connection.

```bash
ssh vboxuser@10.0.0.10
```

Possible error messages included:

```
Connection timed out
```

or

```
Connection refused
```

SSH access was no longer available.

---

# Troubleshooting Process

## Step 1 — Test Basic Network Connectivity

First, verify that the server is reachable.

```bash
ping -c 4 10.0.0.10
```

Result:

- Ping succeeded.
- No packet loss occurred.

### Conclusion

The problem was **not** related to:

- Incorrect IP addressing
- Incorrect subnet
- Routing
- VirtualBox networking
- Network connectivity

Since ICMP traffic was successful, the server itself was reachable.

---

## Step 2 — Verify SSH Service

Using the VirtualBox console, verify the SSH daemon.

```bash
sudo systemctl status ssh
```

Result:

```
Active: active (running)
```

### Conclusion

The SSH service itself was operating correctly.

The issue was likely occurring before traffic reached the SSH daemon.

---

## Step 3 — Verify Port 22 is Listening

Check whether SSH is listening on TCP port 22.

```bash
sudo ss -tulpn | grep :22
```

Result:

<img width="1001" height="52" alt="image" src="https://github.com/user-attachments/assets/cdbd75c5-d1a4-4ba3-b722-4ca20b0cd3d1" />


```
LISTEN
```

### Conclusion

SSH was actively listening for incoming connections.

This ruled out:

- SSH configuration issues
- Service failures
- Incorrect listening ports

---

## Step 4 — Inspect Firewall Rules

Check the current UFW configuration.

```bash
sudo ufw status
```

Result:

The SSH rule allowing TCP port 22 was missing.

Example:

```
80/tcp     ALLOW
443/tcp    ALLOW
```

Notice that:

```
22/tcp
```

was absent.

### Root Cause

The firewall was blocking inbound SSH traffic because port 22 was no longer permitted.

---

# Resolution

Re-add the SSH firewall rule.

```bash
sudo ufw allow ssh
```

Verify the configuration.

```bash
sudo ufw status
```

Expected output:

```
22/tcp ALLOW Anywhere
```

# Verification

Attempt to SSH again from Kali.

```bash
ssh vboxuser@10.0.0.10
```

Result:

The SSH connection was successfully established.

The issue was resolved.

# Troubleshooting Flow

```
SSH Connection Failed
          │
          ▼
Can the server be pinged?
          │
        Yes
          │
          ▼
Is SSH running?
          │
        Yes
          │
          ▼
Is port 22 listening?
          │
        Yes
          │
          ▼
Check firewall rules
          │
          ▼
SSH rule missing
          │
          ▼
Allow port 22
          │
          ▼
SSH restored
```

# Skills Practiced

- Layered network troubleshooting
- Identifying differences between network connectivity and application accessibility
- Using ICMP to verify basic connectivity
- Managing Linux services with `systemctl`
- Inspecting listening ports using `ss`
- Configuring firewall rules with UFW
- Verifying service availability
- Root cause analysis
- Testing after implementing a fix
- Following a structured troubleshooting methodology

---

# Key Takeaways

- Successful ping responses do not guarantee that application services are accessible.
- A running service can still be unreachable if the firewall blocks the required port.
- Troubleshooting should begin with the simplest checks before investigating more complex causes.
- Verifying each layer of the network stack helps isolate problems quickly.
- Always confirm the solution by retesting the original issue after making changes.
