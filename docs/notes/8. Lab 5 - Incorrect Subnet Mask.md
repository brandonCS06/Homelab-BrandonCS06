# Network Troubleshooting Lab 5: Incorrect Subnet Mask

## Objective

Practice identifying and resolving a network connectivity issue caused by an incorrect subnet mask while using a VirtualBox homelab. The goal was to diagnose the issue using common Linux networking tools instead of immediately checking the network configuration.

---

# Lab Environment

| Machine | IP Address | OS |
|----------|------------|----|
| Ubuntu Server | 10.0.0.10 | Ubuntu Server |
| Ubuntu Desktop | 10.0.0.20 | Ubuntu Desktop |
| Kali Linux | 10.0.0.30 | Kali Linux |

Network: **10.0.0.0/24**

---

# Scenario

The Ubuntu Desktop suddenly lost connectivity to the Ubuntu Server.

Symptoms:

- Unable to ping the server
- Unable to SSH into the server
- Network interface appeared to be functioning normally

The objective was to determine the root cause through a structured troubleshooting process.

---

# Initial Verification

Before intentionally breaking the network, connectivity was confirmed.

Verified IP configuration:

```bash
ip -br addr
```

Verified connectivity:

```bash
ping 10.0.0.10
```

Verified SSH:

```bash
ssh vboxuser@10.0.0.10
```

Everything worked as expected.

---

# Breaking the Network

On the Ubuntu Desktop, the subnet mask for the internal network interface (**enp0s8**) was intentionally changed.

### Original Configuration

| Setting | Value |
|----------|-------|
| IP Address | 10.0.0.20 |
| Subnet Mask | 255.255.255.0 (/24) |

### Broken Configuration

| Setting | Value |
|----------|-------|
| IP Address | 10.0.0.20 |
| Subnet Mask | 255.255.255.240 (/28) |

The IP address remained the same, but the subnet mask changed.

# Troubleshooting Process

## Step 1 - Verify Interface Configuration

Command:

```bash
ip -br addr
```

Observed:

```
10.0.0.20/28
```

The IP address was correct, but the subnet mask was different than expected.

---

## Step 2 - Examine the Routing Table

Command:

```bash
ip route
```

Output:

<img width="597" height="73" alt="image" src="https://github.com/user-attachments/assets/3e0c5d54-0a46-4512-9ff0-c6436d0af2be" />


### Analysis

The desktop believed the local network was:

```
10.0.0.16/28
```

Usable addresses:

```
10.0.0.17
through
10.0.0.30
```

The Ubuntu Server:

```
10.0.0.10
```

was **outside** of this subnet.

Because of this, Linux attempted to send packets toward the default gateway instead of communicating directly with the server.

---

## Step 3 - Inspect the ARP Table

Command:

```bash
ip neigh
```

Output:

```
10.0.2.2 dev enp0s3 ...
fd17:625c:f037:2::2 ...
fe80::2 ...
```

Noticeably absent:

```
10.0.0.10
```

### Analysis

No ARP entry existed for the Ubuntu Server.

Since the desktop believed the server was on another network, it never attempted to discover the server's MAC address using ARP.

This confirmed the issue was occurring before Layer 2 communication could even begin.

---

# Root Cause

The subnet mask was configured incorrectly.

The desktop believed the server was located on a different subnet, causing all traffic destined for the server to be forwarded toward the default gateway rather than sent directly across the local network.

---

# Resolution

The subnet mask was restored.

### Correct Configuration

| Setting | Value |
|----------|-------|
| IP Address | 10.0.0.20 |
| Subnet Mask | 255.255.255.0 (/24) |


Output now included:

# Key Takeaways

- A device can have the **correct IP address** but still be unable to communicate if the subnet mask is incorrect.
- The subnet mask determines whether a destination is considered local or remote.
- If a host is believed to be remote, traffic is sent to the default gateway instead of directly to the destination.
- An incorrect subnet mask can prevent ARP from ever occurring because the host does not attempt Layer 2 communication with devices it believes are on another network.
- Using tools such as `ip addr`, `ip route`, and `ip neigh` provides a systematic way to isolate networking issues instead of relying on guesswork.
